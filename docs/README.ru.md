# AI Wiki — плагин Obsidian

[English version →](../README.md)

Автоматически строит и пополняет базу знаний из ваших заметок с помощью ИИ-ассистента.

**Почему AI Wiki:**
- **Офлайн по умолчанию** — работает с Ollama или любым локальным ИИ-сервером; ваши заметки не уходят с вашего компьютера
- **Растёт вместе с заметками** — каждый Ingest добавляет новые темы и автоматически обновляет существующие
- **Прозрачность** — каждый шаг ИИ виден в реальном времени в боковой панели
- **Единый OpenAI-совместимый runtime** — локальный Ollama или удалённый совместимый сервис

> Поддерживаемый transport: **OpenAI-совместимый**, включая локальный Ollama и удалённые сервисы.

---

## Что умеет плагин

AI Wiki читает ваши заметки и ведёт структурированную базу знаний (вики) рядом с ними. Представьте ассистента, который читает всё, что вы пишете, и автоматически поддерживает актуальный справочник.

| Функция | Что делает |
|---|---|
| **Ingest** | Читает открытую заметку, извлекает ключевые темы (люди, инструменты, процессы, термины), создаёт страницы или обновляет существующие защищёнными патчами секций. Большой Markdown обрабатывается ограниченными чанками с полным покрытием evidence. Теги стандартизированы: страницы переиспользуют существующий словарь тегов домена, несут тег своего типа сущности, а число тематических категорий тегов ограничено настройкой домена |
| **Query** | Отвечает на вопрос, используя вики как источник; ответ появляется в панели с перекрёстными ссылками |
| **Lint** | Проверяет страницы вики на пробелы, устаревший контент и битые ссылки; выдаёт отчёт в панели |
| **Fix** | После Lint — введите инструкцию в чат панели, и ИИ применит правки |
| **Init** | Создаёт новую область знаний (домен): структуру папок, `metadata.jsonl`, `index.jsonl` и `log.jsonl` |
| **Re-init** | Удаляет и заново создаёт всё дерево домена, включая метаданные и пустые папки, затем пересобирает его из источников |
| **Format** | Улучшает форматирование любой открытой заметки (вне вики): заголовки, таблицы, frontmatter, подписи к изображениям. Показывает предпросмотр перед применением. Инвариант: факты не добавляются и не удаляются — только улучшается ясность изложения. Если заметка принадлежит настроенному домену, теги переиспользуются из существующего словаря тегов этого домена |
| **Chat** | Интерактивный диалог в боковой панели после Query или Lint для уточнения результатов |
| **Export OKF** | Сериализует домен в бандл Google [Open Knowledge Format](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing/) — папку markdown с OKF-frontmatter, сгенерированными `index.md`/`log.md` и обычными ссылками `[текст](ссылка.md)` — для обмена с внешними AI-агентами и инструментами. Только на компьютере |

Fix, Format и Chat запускаются из кнопок в боковой панели — не через палитру команд. Export OKF доступен и как кнопка в панели, и как команда палитры.

> **Мобильные устройства:** работает только Query. Ingest, Lint, Init, Format и Export OKF — только на компьютере.

> **OKF-frontmatter:** страницы вики используют Google Open Knowledge Format — обязательный `type` (подпапка типа сущности) плюс `description`/`resource`/`timestamp`/`tags`/`status`. Граф знаний живёт в body-секциях `## Related` / `## External links` (на диске — Obsidian-`[[wikilinks]]`, переписываются в markdown-ссылки только при OKF-экспорте).

## Раскрытие информации для каталога сообщества

### Использование сети

AI Wiki отправляет выбранное содержимое заметок и промты только в настроенный пользователем OpenAI-совместимый сервис. Endpoint может быть локальным, например Ollama, или удалённым. Сеть используется только для запущенных пользователем AI-операций и опциональных проверок модели.

### Аккаунты и оплата

Сам AI Wiki бесплатен и не требует аккаунта. Для локального Ollama не нужны аккаунт и оплата. Опциональные удалённые OpenAI-совместимые сервисы могут требовать собственный аккаунт или оплату.

### Доступ к внешним файлам

AI Wiki не запускает пользовательский AI CLI или другой внешний AI-процесс.

### Доступ к хранилищу

Плагин читает только папки, которые вы указали как источники для каждого домена. Полный обход хранилища не выполняется.

### Лицензия

AI Wiki распространяется по [лицензии Apache 2.0](../LICENSE).

## Локальная разработка и релизы

Версия `0.3.11` поддерживает Obsidian `1.13.0` и новее, включая мобильные устройства (`isDesktopOnly: false`). UI настроек использует поддерживаемый Obsidian API **Settings Definitions**: индексируемые группы и элементы управления возвращаются как definitions, а нестандартные поддерживаемые контролы отрисовываются через callback `render` соответствующего definition. Устаревший lifecycle `display()` не используется.

Официальная команда lint для исходников — `npm run lint`. Она применяет полную рекомендованную конфигурацию `eslint-plugin-obsidianmd` к исходникам репозитория вне фиксированных исключений Community scanner и допускает **ноль ошибок и ноль предупреждений** (`--max-warnings 0`).

Мобильную оценку запускают после пересборки её bundle:

```bash
npm run eval:mobile-fixes:build
node tests/eval/mobile-fixes/run.cjs
```

Проверка релиза состоит из двух фаз. До production build она сканирует только отслеживаемые текстовые файлы в `src/`, `tests/eval/` и `scripts/`; `scripts/dspy/CLAUDE.md` и `scripts/validate-release.mjs` — явные исключения. Совпавшая диагностика имеет точный вид `[<path>] forbidden <category> marker: <match>` и использует категории: Claude backend, Claude CLI probe, subprocess, Claude configuration и Claude UI. После build валидатор напрямую сканирует `dist/main.js` (даже если файл не отслеживается), отклоняет inline source map и требует непустые `dist/main.js`, `dist/manifest.json` и `dist/styles.css`, причём source и distribution manifest должны совпадать побайтно.

Остальные release gates запускаются в таком порядке: `npm run audit:all`, `npm run release:validate:pre`, `npm run lint`, `npm run typecheck`, `npm test`, указанная выше мобильная оценка, `npm run build`, затем `npm run release:validate:post`. Полный audit отклоняет известные уязвимости runtime- и development-зависимостей; `npm run audit:prod` остаётся доступным для проверки только runtime-графа. Репозиторий отслеживает точные сгенерированные release-файлы, а workflow требует, чтобы build не оставил diff в этих отслеживаемых файлах.

История релизов неизменяема: `versions.json["0.3.5"]` остаётся `"1.7.2"`. Метаданные текущей `0.3.11` в package, lockfile, source/root/distribution manifest синхронизированы; `0.3.11` сопоставлена с `1.13.0`, и каждый текущий manifest указывает ту же минимальную версию приложения.

Release workflow срабатывает на push в `master`, изменяющий `src/manifest.json`; обычная поставка достигает его через merge pull request, но YAML не проверяет происхождение merge. Его одна постоянная concurrency-группа ставит ожидающие публикации в очередь (`queue: max`) и не отменяет активный run. После всех gates, вычисления asset digest и provenance attestation workflow делает только non-force lightweight tag claim для проверенного commit `GITHUB_SHA` и один create-only `gh release create`; draft, partial, conflicting или ambiguous состояние релиза останавливает публикацию. Уже завершённый совпадающий релиз — terminal success без мутации.

Отправка в Community plugin directory, действия с аккаунтом или review и изменение directory metadata остаются вне поставки и не авторизованы этим процессом релиза.

## Быстрый старт: Ollama (полностью локально)

Не нужны аккаунты и облачные сервисы — ИИ работает на вашем компьютере.

### 1. Установите Ollama

Скачайте с [ollama.com](https://ollama.com) и загрузите модель:

```bash
ollama pull llama3.2
```

### 2. Установите плагин

Установите **AI Wiki** через Настройки → Сторонние плагины → Обзор.

Для ручной установки скачайте `main.js`, `manifest.json` и `styles.css` одной версии со
страницы GitHub Releases. Положите три файла непосредственно в
`<vault>/.obsidian/plugins/ai-wiki/`, затем перезапустите Obsidian и включите плагин.

Для локальной разработки соберите проект:

```bash
npm install
npm run build
```

Затем скопируйте или подключите символической ссылкой каталог `dist/` как
`<vault>/.obsidian/plugins/ai-wiki/`. Подключайте `dist/`, не корень репозитория: каталог
плагина должен содержать плоский набор `main.js`, `manifest.json` и `styles.css`.

### 3. Включите плагин

Obsidian → Настройки → Сторонние плагины → найти «AI Wiki» → включить.

### 4. Настройте

Настройки → AI Wiki:

| Параметр | Значение |
|---|---|
| Base URL | `http://localhost:11434/v1` |
| API Key | `ollama` |
| Модель | `llama3.2` |
| Temperature | `0.2` |
| Семантическое сжатие | `Сбалансированное` |

Бюджеты токенов ввода и вывода по умолчанию автоматические — AI Wiki выводит их из
context window модели, так что настраивать здесь нечего. Оставьте поля пустыми, если не
нужно переопределить автоматическое значение; см. [Ограниченная обработка и storage](#ограниченная-обработка-и-storage).

### 5. Создайте область знаний (домен)

Домен — это пара: «папка с источниками → папка вики». ИИ читает заметки из папки источников и создаёт страницы вики в папке вики.

Откройте боковую панель AI Wiki (иконка 🧠 на ленте или Палитра команд → «Открыть панель»), затем:

1. Нажмите кнопку **Init** в секции «Создание»
2. Введите название домена (например, `work` или `проекты`)
3. Укажите пути к папкам с заметками-источниками
4. Нажмите **Запустить** — плагин создаст структуру вики и начнёт наполнять её

### 6. Первый Ingest

1. Откройте любую заметку в Obsidian
2. В боковой панели выберите нужный домен в выпадающем списке
3. Нажмите кнопку **Ingest**
4. Следите за прогрессом в боковой панели — новые страницы вики появятся в папке домена

## Боковая панель

Боковая панель — главный интерфейс AI Wiki. Откройте её через иконку 🧠 на ленте или Палитру команд → «Открыть панель».

### Секции

**Создание** — кнопка **Init**: создать новый домен (название, папка вики, папки источников).

**Наполнение / Актуализация** — работа с существующим доменом:
- Выпадающий список доменов
- **↻** обновить список доменов
- **📁+** управление источниками (добавить или удалить папки источников)
- **♻** полный Re-init: удалить и заново создать всё дерево домена, затем пересобрать из источников
- 📜 открыть лог-файл домена
- 🗒 открыть индексный файл домена
- **Ingest** — обработать текущую открытую заметку
- **Lint** — проверить качество вики
- **Format** — улучшить форматирование текущей заметки

**Запрос** — введите вопрос и нажмите **Спросить**. Ответ появится в панели со ссылками на страницы вики. Используйте чат ниже для уточнений.

### Прогресс модели и Re-init

Каждый запрос к модели проходит один понятный lifecycle в панели: **Подготавливаем запрос →
Запрос передан модели → Ожидаем ответ модели → Модель формирует ответ → Проверяем ответ →
Применяем результат → Готово** (либо завершается повтором, ошибкой или отменой).
Рассуждение остаётся в раскрываемом блоке. Call site, transport, номер попытки, бюджеты и
данные провайдера сохраняются только в `agent.jsonl`, но не в подписях панели. Таймер
ожидания показывает прошедшее время в UI: это не heartbeat провайдера, и idle deadline он
не продлевает. В agent log рассуждение сохраняется упорядоченными ограниченными записями
до 4 MiB на операцию; лишний текст заменяется marker обрезки только с метаданными.

В OpenAI-совместимом runtime новая transport-попытка начинает новый понятный lifecycle с состояния
**Подготавливаем запрос**. Боковая панель не показывает счётчики повторов и HTTP-детали.
В `agent.jsonl` сохраняются только метаданные событий `transport_retry_scheduled`,
`transport_retry_recovered` и `transport_retry_exhausted`: logical request ID, lifecycle
ID, status/classification, задержка, граница попыток и таймауты. Тело запроса, ответ модели,
authorization headers и API keys в retry-диагностику не попадают.

Фоновые structured-вызовы — bootstrap Init, evidence map/reduce, synthesis Ingest и
ограниченные batch-вызовы Lint — получают атомарный non-stream ответ. Интерактивные Chat,
ответ Query и Format используют SSE, поэтому рассуждение или текст ответа видны по мере
поступления.

Полный Re-init до изменений проверяет bootstrap и снимки источников, затем ровно один раз
удаляет всё дерево `!Wiki/<domain>`: страницы, метаданные, индексы, логи, временные данные,
вложенные папки типов и устаревшие пустые каталоги. Перед ingest создаются свежие metadata
и index. Ошибка удаления или конфликт параллельной записи останавливает ingest; транзакция
восстанавливает прежний снимок, когда это безопасно, и не перезаписывает параллельно
созданное дерево домена.

## Справочник настроек

### Общие

| Параметр | Описание | По умолчанию |
|---|---|---|
| User prompt | Добавляется в конец системного промта каждой операции | пусто |
| Таймауты (секунды) | `ingest/query/lint/init/format` через `/` | `300/300/900/3600/600` |
| Idle timeout LLM | Максимальная пауза между значимыми событиями native-модели; `0` отключает executor idle deadline | `300` с |
| Число повторов | Дополнительные попытки текущего OpenAI-совместимого запроса | `3` |
| Лимит истории | Максимум операций в истории боковой панели | `20` |
| Лог агента (JSONL) | Запись событий агента в служебный JSONL-файл плагина (только компьютер) | выкл |

### Домены

Список созданных доменов с кнопками **Редактировать** / **Удалить**. Каждый домен самодостаточен: настройки и типы сущностей хранятся в `!Wiki/<domain>/metadata.jsonl`, retrieval-индекс и векторы — в `!Wiki/<domain>/index.jsonl`, история операций — в `!Wiki/<domain>/log.jsonl`.

### OpenAI-совместимый runtime

| Параметр | Описание | По умолчанию |
|---|---|---|
| Base URL | OpenAI-совместимый endpoint. Ollama: `http://localhost:11434/v1` | `http://localhost:11434/v1` |
| API key | `ollama` для Ollama; `sk-...` для OpenAI | `ollama` |
| Таймаут соединения | Только установка DNS/TCP/TLS на компьютере; не ограничивает headers, body или генерацию | `15` с |
| Контекстное окно модели | Сколько токенов модель вмещает в один запрос. Своё поле есть у чат-модели, у каждой модели по операциям и у vision-модели, поэтому модели разного размера считаются раздельно. Пусто (показано как «Автоматически») — автоматический режим: окно читается у бэкенда. Число задавайте, только если бэкенд его не сообщает; тогда все бюджеты этой модели выводятся из него, а опрос не выполняется. Минимум — `1024` токена, меньшие значения не принимаются | *(пусто = Автоматически)* |
| Бюджет токенов ввода | Максимальный размер упакованного промта. Пустое значение (показано как «Автоматически») выводится из context window модели: определяется один раз для модели, кешируется и самокорректируется по фактическому расходу токенов от провайдера. Число в поле — явное переопределение | *(пусто = Автоматически)* |
| Бюджет токенов вывода | Лимит ответа, передаваемый через `maxTokens`/API `max_tokens`. Пустое значение (показано как «Автоматически») выводится так же, отдельно для каждой операции. Число в поле — явное переопределение | *(пусто = Автоматически)* |
| Семантическое сжатие | Профиль плотности промта (`Максимальное`/`Сбалансированное`/`Минимальное`) с правилами сохранения данных для каждой операции | `Сбалансированное` |
| Модель | Имя модели (`llama3.2`, `mistral`, `gpt-4o`, …). Показывается когда per-operation выключен | `llama3.2` |
| Бюджет токенов размышления | Отдельный лимит рассуждения native-модели; `0` или пустое значение отключает его. Бюджет ввода при этом не увеличивается | выкл |
| Temperature | `0.0`–`1.0`. Низкие значения (`0.1`–`0.3`) дают более точные и фактические ответы | `0.2` |
| Модели по операциям | Когда включён — отдельные модель, бюджеты ввода/вывода, сжатие, бюджет размышления и temperature для каждой операции. Format сохраняет числовые бюджеты, но не имеет настройки семантического сжатия | выкл |
| Повторы восстановления ответа | Повторы при невалидном JSON или невалидном framed-ответе после Zod validation (0–3). Выше = надёжнее на слабых моделях | `1` |

### Восстановление transient-запросов

AI Wiki повторяет только текущий идентичный OpenAI-compatible запрос в пределах
настроенного числа дополнительных попыток. Init, Re-init, Ingest, чтение источника,
`WipeDomain`, завершённая evidence-обработка и применение страницы/индекса не запускаются
заново. Разрешены повторы connection errors/timeouts и HTTP `408`, `409`, `429`, `5xx`.
Заголовок провайдера `x-should-retry: true` может разрешить другой transient-ответ, а
`x-should-retry: false` всегда запрещает повтор. HTTP `400`, `401`, `403`, `404`, `422`,
context-limit и schema errors, отмена, постоянные TLS/certificate errors и ошибки
application/index/embedding не повторяются на transport-уровне.

Сохранённая retry-диагностика принимает только классы connection, connection timeout,
разрешённые temporary transport, retryable HTTP и явный provider override. Transport-классы
не содержат HTTP status; HTTP-классы обязаны содержать согласованный валидный status, а
recovered/exhausted diagnostics должны совпадать с закрываемой scheduled failure.

После непустого reasoning или content повтор запрещён; исчерпание границы завершает
операцию ошибкой. Таймаут соединения (`15` секунд), idle timeout модели (`300` секунд) и
число повторов (`3`) — независимые top-level настройки; сохранённые значения не
перезаписываются. Здоровый ответ может длиться больше 15 секунд, потому что этот таймаут
относится только к установке desktop-соединения. На Mobile используется host transport,
поэтому точный DNS/TCP/TLS-only timeout не гарантируется; request retry и model idle не
объединяются с этим ограничением.

### Ограниченная обработка и storage

Эти настройки относятся к разным частям вызова: **Бюджет токенов ввода** ограничивает
подготовленный запрос, **Бюджет токенов вывода** — сгенерированный ответ, а **Бюджет
токенов размышления** отдельно разрешает рассуждение модели, если провайдер его
поддерживает. Всеми тремя настройками управляет AI Wiki.

Бюджет ввода ограничивает весь подготовленный запрос, включая system/schema-инструкции,
а не только текст заметки. Если данные не помещаются, AI Wiki упаковывает целые единицы
контекста и применяет batching или разбиение для конкретной операции вместо скрытого
обрезания обязательного контента. После context error провайдера запрос может быть
переупакован с меньшим бюджетом.

Пустой бюджет ввода или вывода означает автоматический режим: AI Wiki
определяет context window модели один раз для модели, кеширует его и самокорректирует
оценку по фактическому расходу токенов, который сообщает провайдер. Число, введённое в
поле «Бюджет токенов ввода» или «Бюджет токенов вывода», по-прежнему действует как явное
переопределение — автоматический режим никогда не перезаписывает заданное вами значение.

Если провайдер не сообщает context window модели, AI Wiki использует консервативное
запасное окно в **8192 токена** и считает бюджеты от него. Запасное значение кешируется на
**24 часа**, поэтому следующий запуск после этого срока снова опрашивает провайдера и
подхватывает настоящее окно, как только оно появится; найденное окно кешируется без срока
годности. По ёмкости это запасное значение примерно эквивалентно прежнему байтовому
бюджету 16384 — около 15 кБ латинского текста в обоих случаях, — то есть изменилась
единица измерения, а не размер допуска.

#### Если бэкенд вообще не сообщает окно

Некоторые OpenAI-совместимые бэкенды — прежде всего агрегирующие шлюзы и прокси —
отвечают на `GET /v1/models` и перечисляют вашу модель, но ни одна запись не содержит
context length, а Ollama-эндпоинта `/api/show` у них нет. Определять тогда нечего, и
каждый запуск считает бюджеты от консервативного запасного окна в 8192 токена, хотя
реальное окно модели может быть в шестнадцать раз больше. Как это выглядит: блоки схемы
или инструкций выбрасываются из промта, чтобы он поместился; запросы сообщают об
усечении («нужно N токенов» против лимита в 4096 токенов, а сам этот лимит выведен из
фантомного окна 8192); в `agent.jsonl` видно `contextWindow: 8192` и
`inputSource: "default"`. Agent-лог **по умолчанию выключен** — включите **Лог агента
(JSONL)** в настройках, прежде чем искать эти записи. В самом поле при неизвестном окне
показано «Автоматически»: запасное значение — не измерение вашей модели, поэтому оно
никогда не выдаётся там за измеренное.

Решение — заполнить **Контекстное окно модели** реальным окном модели в токенах
(например, `131072`; минимально принимается `1024`). После этого AI Wiki полностью
пропускает опрос для этой пары «бэкенд + модель» и выводит из вашего числа все бюджеты,
ровно так же, как если бы окно сообщил сам бэкенд: бюджет ввода, бюджет вывода, потолок
вывода для каждого запроса, бюджеты чанков и разбиение bootstrap-данных в Init. В
agent-логе появляется `inputSource: "configured"` — видно, что число задали вы. Очистка
поля возвращает модель к автоматическому определению.

Окно принадлежит той модели, рядом с которой стоит поле, а не бэкенду: у чат-модели, у
каждой модели по операциям и у vision-модели своё поле **Контекстное окно модели**, и
очистка одного не затрагивает остальные. Две роли с одинаковым именем модели используют
одно окно, потому что плагин хранит одну запись контекста на модель.

Введённое здесь значение считается инструкцией, а не догадкой: если провайдер позже
отклонит запрос и сообщит собственное меньшее окно, AI Wiki **не** уменьшит ваше значение
молча. Расхождение записывается в `agent.jsonl` как запись `context_window_conflict` с
обоими числами, чтобы вы могли поправить настройку сами. (Найденное или запасное окно,
которое никто не выбирал, в такой ситуации по-прежнему уменьшается автоматически.)

Дальнейшее поведение зависит от того, какая это операция. Ingest, Query и Lint — а также
чат-продолжения — переупаковывают отклонённый запрос в меньший бюджет и всё равно
завершаются. **Init так не может:** он планирует разбиение bootstrap-данных по окну *до*
отправки запросов, поэтому окно, заданное больше реального, приводит к ошибке bootstrap, а
не к уменьшению запроса. Расхождение при этом всё равно записывается, так что причина видна в
`agent.jsonl`; уменьшите настройку до реального окна модели (или очистите поле, вернув
автоматический режим) и запустите заново.

Включение режима **Модели по операциям** не отключает автоматические бюджеты. У каждой
операции появляются собственные поля бюджета ввода и вывода, и каждое из них автоматическое,
пока оно пустое. Введённое число переопределяет автоматическое значение только для этой
операции; очистка поля возвращает операцию в автоматический режим.

Если вы обновились с версии, где эти поля требовали число, AI Wiki один раз спросит,
переключить ли сохранённое значение на автоматическое или оставить его; если закрыть этот
диалог без ответа, сохранённое значение остаётся как есть. Изменить решение можно в любой
момент — очистив или заново задав поле в настройках, включая поля по операциям: очищенное
значение остаётся очищенным и после перезапуска.

Оценщик промта считает токены, а не сериализованные байты, и оценивает символы по классам:
команды оболочки, конфиги, пути и JSON стоят намного больше токенов на символ, чем проза,
поэтому заметки, состоящие из них, больше не оцениваются как проза. Из-за обоих изменений
сместились границы чанков при ingest. Существующие домены **не** переиндексируются
автоматически после обновления — запустите **♻ полный Re-init** (`--force`) на боковой
панели для домена, чтобы перестроить его с новым разбиением на чанки.

Ingest делит большой Markdown по стабильным границам секций, абзацев, окон строк и
fenced-code блоков. Ограниченные map-вызовы создают evidence с привязкой к источнику, а
reduce-вызовы сохраняют полное покрытие до synthesis. Новые страницы создаются целиком.
Существующие получают защищённые хешами страницы/секции патчи `add`, `append` или
`replace`: нетронутые секции сохраняются, а устаревшее состояние не перезаписывается.

`index.jsonl` — структурированное хранилище: `page` records содержат retrieval-метаданные,
а `chunk` records — метаданные эмбеддингов и векторы. Сериализованные векторы и сырые
records индекса никогда не попадают в промты модели; prompt builders передают только
нужные выбранные evidence, Markdown-секции и разрешённые метаданные. Неизменившиеся
эмбеддинги чанков переиспользуются, если совпадают хеш embedding-текста, модель и
размерность.

Маленькие источники сохраняют короткий путь обработки. Большие источники, страницы,
истории, заметки или PDF могут потребовать дополнительных ограниченных вызовов модели:
это увеличивает задержку и стоимость провайдера в обмен на полную обработку в заданном
бюджете ввода. Vision Check — тоже реальный запрос провайдеру и может стоить небольшую
сумму.

Анализ изображений и PDF считается по context window **vision**-модели, а не по окну
чат-модели, которая выполняет Format. У vision-модели есть собственная
запись контекста — полученная от бэкенда или взятая из её собственного поля **Контекстное
окно модели**, — и число страниц PDF в одном vision-запросе выводится из неё. Поэтому
vision-модель с небольшим окном разбивает PDF на большее число меньших вызовов вместо
одного слишком большого запроса, который провайдер отклонит. Меняется только окно:
значения **Бюджет токенов ввода** и **Бюджет токенов вывода**, заданные для операции
Format, по-прежнему ограничивают и vision-вызов.

Это работает только тогда, когда окно vision-модели действительно **известно**. Если
бэкенд его не сообщает, а вы ничего не задали, vision по-прежнему считается по бюджету
самой операции Format, как и раньше: консервативное запасное окно в 8192 токена — это не
измерение вашей vision-модели, и расчёт по нему оставил бы меньше места, чем стоит одно
изображение, то есть отклонял бы каждое вложение ещё до отправки. Поэтому на бэкенде,
который ничего не сообщает, поле **Vision → Контекстное окно модели** и есть то, что
заставляет работать vision-модель с небольшим окном: задайте реальное окно модели, и от
него будут выведены разбиение PDF на батчи, лимит вывода и клиентская проверка размера.

Vision-вызовы пополняют хранилище контекста наравне с остальными. Vision-вызов сообщает
собственный расход, поэтому модель, работающая только как vision, уточняет калибровку
токенов по своим же запросам, а не остаётся на 1, и отказ провайдера по vision-запросу
запоминается за этой моделью, а не только обрабатывается внутри запуска — следующий
запуск больше не повторяет ту же завышенную первую попытку.

Ответ vision — это описание одной картинки, поэтому он занимает четверть окна, а не
половину, которую забирает переписывание в Format. Именно это делает небольшое окно
рабочим: ниже примерно 7100 токенов ни одно окно не вмещает картинку, и поле
**Vision → Контекстное окно модели** сообщает об этом под полем, если заданное вами
число ниже этого порога.

Если вложение пропущено из-за размера, предупреждение `⚠️ Vision skipped` объясняет
причину: называет vision-модель и настройку, которую надо изменить, а когда окно известно
— ещё и само окно, по которому считался запрос, и откуда это число (задано вами, получено
от бэкенда или уточнено по отказу провайдера). Когда окно неизвестно, никакого числа в
сообщении нет, потому что его и нет: там сказано, что бэкенд не сообщает окно для этой
модели и запрос считался по бюджету самой операции Format. Такие отказы происходят до
отправки запроса, поэтому в ответе провайдера объяснения нет и быть не может. Текст
предупреждения выводится на английском независимо от языка интерфейса.

Приёмку разрушительного Re-init проводят только в приватной копии, не в рабочем vault.
Protected replay root должен быть свежим каталогом
`/tmp/ai-wiki-bounded-ingest-replay.*` с owner-only marker `.replay-provenance`, где
записаны resolved source и replay root. Build устанавливают в копию `run`, затем в
Obsidian вручную проверяют путь открытого vault и только после этого выполняют human
Re-init checkpoint. Read-only auditor отклоняет повторный wipe, source/page/index effects,
неверные retry lifecycle и таймауты, retry после content и recovery без перехода к
следующему шагу. После transport recovery допустим коррелированный structured-repair
lifecycle перед успешными validation/application/completion. Page mutation считается
эффектом только после соответствующего успешного `tool_result`; metadata-only index
checkpoints связывают обе стадии index reconciliation с активным source и выбранным domain.

## Синхронизация

Файл `local.json` (внутри папки плагина) хранит OpenAI API key, пароль прокси, записи о context window моделей и другое локальное состояние компьютера. **Исключите `local.json` из синхронизации** при использовании Obsidian Sync / git / Syncthing — иначе настройки будут перезаписаны на других машинах.

Файлы домена (`metadata.jsonl`, `index.jsonl`, `log.jsonl` внутри `!Wiki/<domain>/`) находятся внутри хранилища и синхронизируются вместе с заметками в обычном режиме. `local.json` остаётся локальным и не должен синхронизироваться.

## Ориентиры по производительности

Реальные замеры на домашнем сервере с моделью **`deepseek-v4-flash:cloud`** через OpenAI-совместимый endpoint. Скорость генерации — около 100–130 токенов/с, что соответствует средней локальной или самостоятельно хостящейся GPU.

| Операция | Типичная длительность | Вызовов LLM | Вх. токенов (avg/вызов) | Вых. токенов (avg/вызов) | Скорость (tok/s) |
|---|---|---|---|---|---|
| **Query** | 4–14 с | 1 | ~6 800 | ~470 | ~100 |
| **Ingest** (1 заметка) | ~25 с | 2 | ~4 300 | ~1 200 | ~109 |
| **Init** (6–24 файла-источника) | 6–27 мин | 20–35 на сессию | ~5 700 | ~2 600 | ~122 |
| **Lint** (большой домен) | ~60 мин | 69 | ~14 300 | ~6 500 | ~128 |

> **Init** и **Lint** масштабируются по числу файлов и страниц вики. Домен из 6 файлов — ~6 мин; из 24 файлов — ~27 мин. Lint большого домена (69 вызовов LLM) занял около 60 мин.

### Что влияет на скорость

- **Модель** — меньшие/квантованные модели быстрее; более крупные дают лучшее качество вики
- **Сервер вывода** — локальная GPU быстрее всего; облачные API добавляют сетевую задержку
- **Размер домена** — время Init и Lint растёт линейно с числом файлов
- **Большие входные данные** — ограниченные map/reduce, batching и сегментация добавляют вызовы ради полного покрытия
